# Runtime systems

Last updated: 2026-10-14

- Camera/inference: RoomSpellDetection starts capture on request, warms the provider, serializes inference, and pauses capture during puzzles/app pause. Camera errors appear on the board. Candidate confirmation requires confidence ≥0.5 in two consecutive passes, deduplicates labels and drops absent labels.
- Gameplay: RoomSpellGame owns the three selections, current round, occupied tile indices, solved answer history and score. WordCatalog supplies theme-related answers. PuzzleRound prevents tile reuse and validates answer/object constraints.
- UI: RoomSpellBoard uses TMP, a world-space canvas and standard Unity buttons. Its callbacks are wired to the game. It exposes camera/dummy mode, candidates, selections, clue, slots, tiles, clear and next actions.
- Input: Meta SDK ray/poke canvas components connect to PointableCanvasModule. In a non-XR Editor session only, the game switches to mouse input. Simulator validation requires XR input to remain enabled.
- Dummy testing: development-only scenarios provide two spaced observation batches through the same candidate filter. They never claim neural recognition.
- Validation: Editor runners use real model fixtures, public board callbacks, active XR state and runtime head override. The PowerShell runner owns launched processes and process-specific runtime selection.

The model does not place 3D boxes over objects. Words are curated, not generated by an LLM. ElevenLabs narration is deferred; see the README follow-up note.

The relation bank accepts the model's exact `tv monitor` and `sofa` labels as well as the common UI names. Scanning retains its camera texture until any pending GPU pass completes, then releases capture; this prevents stopping a round from invalidating inference input.
